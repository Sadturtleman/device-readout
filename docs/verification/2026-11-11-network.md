## Reproduced failures and corrections

The first interface discovery fixture omitted INTERNET. On API 36, the native interface inventory was empty despite a connected default network. Adding the permission in the test APK exposed four interfaces. A denied-context assertion then failed until the adapter explicitly checked the host declaration. Discovery now distinguishes missing permission from an empty inventory; it does not request permission or send an outbound probe.

An event-invalidation implementation re-queried ConnectivityManager after every callback. The API 36 disconnect test reproduced a timeout: five snapshots had been delivered, the last still said Connected/Wifi, but the native default network was absent at test completion. A successful intervening run did not establish correctness; the next repetition reproduced the failure.

Network callbacks now retain their supplied network/capability/link payload. They enqueue deferred snapshot reads through `DeviceCollector.observeReads`; native mapping, data-saver lookup, normalization and timestamping execute on the collection worker with an independent deadline. Thus onLost remains a disconnect even if a later synchronous OS query would still return stale connected data. The public result is still `Flow<Snapshot>`, with equal values preserved. Other state adapters use the same deferred-read path to fetch fresh state. Sensor delivery is unchanged. Android documents the callback ordering and the risks of follow-up synchronous queries in its [NetworkCallback contract](https://developer.android.com/reference/android/net/ConnectivityManager.NetworkCallback).

The API 26 shell Wi-Fi-disable fixture did not actually disable Wi-Fi. Its instrumentation APK now uses its authorized WifiManager operation on API levels below 29 and restores the original state. This code is confined to the test APK; SDK collectors never alter connectivity. API 36 uses the shell fixture, which restores Wi-Fi/mobile-data settings in finally.

## Reproduce

Run `tools/build-android.ps1 -SdkRoot <installed-sdk>`, then use `tools/test-android-device.ps1` with the exact project AVD name and serial:

| Project AVD | Serial used in this checkpoint | Modes |
|---|---|---|
| DeviceReadout_API26 | emulator-5582 | all, batteryEvents, regionalContracts, networkContracts, interfaceHotplug, networkEvents |
| DeviceReadout_API36 | emulator-5586 | all preceding modes, localeEvents, timeZoneEvents; networkEvents repeated three times |

An unrelated AVD occupied port 5584, so this checkpoint uses 5586 for API 36. The project adb server uses port 5047 but can discover other AVDs; the server itself is not an ownership boundary. Never stop, install into or change fixtures on an unmatched AVD. The startup helper checks both console and adb ports before launching.

After verification, both project AVDs reported Wi-Fi/mobile data restored to 1 and ACTIVATE_VPN restored to default. Only those two name-verified AVDs were stopped. The unrelated emulator-5584 remained connected; its adb server was left running.

The interface fixture uses a real VpnService-created TUN with address 192.0.2.1/24 and MTU 1400, restricted to the test APK, with no remote endpoint or default route. The helper restores the test APK's temporary ACTIVATE_VPN app-op. Closing the interface and stopping the test service are in cleanup paths. This is virtual hotplug evidence, not physical adapter coverage.

Raw instrumentation output is under ignored `.tools/DeviceReadout_API<level>-<mode>-results.txt`. The reproduced race is preserved as `.tools/DeviceReadout_API36-networkEvents-race-before-fix.txt`; the three passing repetitions are `...-networkEvents-fixed-run1.txt` through `...run3.txt`. JVM XML is under `kotlin/core/build/test-results/test`; lint reports are under `kotlin/android/build/reports`. Helpers require explicit instrumentation `deviceReadoutStatus=passed` and final code -1, not merely an adb exit code.

## Remaining scope

Physical Wi-Fi/cellular/VPN handovers, interface changes faster than observations, sustained callback overload, initial-read/event ordering, arm64/32-bit Android and the rest of the API/device matrix remain unverified. Network fields do not promise external reachability or a socket's explicitly selected route. Browser/.NET code was unchanged and their prior results were not rerun for this checkpoint.

Android CPU topology, storage, Wi-Fi/current data RAT, eligible restricted identifiers and remaining sensor adapters still need work. Browser/Windows feature completion, Swift/Apple, Flutter/RN, package consumption and the complete supported-environment matrix remain required. The full implementation goal is active.
