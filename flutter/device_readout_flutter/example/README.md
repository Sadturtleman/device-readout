# DeviceReadout Flutter example

`lib/main.dart` observes the widget's registered FlutterView, explicitly selects its current viewport and displays typed snapshots with StreamBuilder. Widget disposal detaches the observer before closing DeviceAccess. The application opens no permission prompts.

The Windows runner builds with Flutter 3.47.9 and Visual Studio C++ desktop tools. From this directory, `flutter pub get` then `flutter run -d windows` runs the interactive example. From the repository root, `./tools/test-flutter-windows.ps1` uses the pinned local SDK, verifies a hidden test-only runner, then leaves the ordinary Release build at `build/windows/x64/runner/Release/device_readout_example.exe`. Keep the accompanying DLLs and data directory with that executable.

`test_support/viewport_windows.dart` and its native Windows test channel are enabled only by the verification script's process-local build flag. They never enumerate or control another application's windows. See [screen verification](../../../docs/verification/2026-11-11-flutter-screens.md).

The Android runner uses min SDK 26 and compile/target SDK 36. `tools/build-flutter-android.ps1` from the repository root builds the separate `test_support/android_sensors.dart` debug entrypoint; `-Target lib/main.dart` selects the ordinary example instead. The harness includes `android_state.dart` for singleton reads, typed errors, equal-value polling and Power events, plus `android_discovery.dart` for native collection/current/selected get/watch. `android_mixed.dart` connects state and sensor adapters to the same public DeviceAccess and verifies concurrent queries, independent cancellation/failure, provider replacement and shared-context closure. The real Activity lifecycle scenario runs in that shared context; its paused callback also checks OS polling and a RAM read. The host independently compares RAM/model/API fields, CPU indices and reported interface names with OS/kernel reads. `/proc/net/dev` avoids API 26 shell restrictions on network sysfs links. The Power check temporarily changes only the owned AVD's simulated power source and restores automatic battery updates; the debug manifest explicitly declares ACCESS_NETWORK_STATE and INTERNET. Ordinary-app wireless/slot queries never open prompts or print identifier/Wi-Fi values.

The sensor scenarios verify actual discovery/measurements, stream cancellation, active teardown, invalid refresh input, app policy preservation and repeated provider replacement. A real Activity background/resume cycle preserves the same watch; native SensorManager diagnostics confirm listener release and recreation. Its blocked RAM collector and replacement altitude source are deliberate fixtures. `tools/test-flutter-android.ps1` also verifies process survival after late replies before stopping the test package. Numbered result fragments prevent Android log truncation from accepting incomplete evidence. Support queries distinguish permission, connected implementations and registered sources; removed handles remain unavailable after rediscovery. The final suite has thirty-three scenarios on each API 26/36.
