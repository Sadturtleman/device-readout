# DeviceReadout for .NET 10

Run `tools/test-dotnet-power-native.ps1` for the additional [23-scenario native power gate](../docs/verification/2026-11-18-dotnet-power-native.md). It builds a Windows SDK C fixture with Visual Studio 2022 C++ tools and runs each case in an owned child. The production P/Invoke path covers native output/failure semantics, real system capabilities and held calls. The ordinary `tools/test-dotnet.ps1` suite remains separate and passes 168/168; both commands are required to reproduce this checkpoint.

The [Windows power-source checkpoint](../docs/verification/2026-11-18-dotnet-power-source.md) corrects ambiguous DC status to a nullable source, verifies get/watch consistency and preserves precise native source notifications. The normal-user suite passes 168/168; restricted-environment failures and remaining hardware/native-path coverage are recorded separately.

The common package generates all 46 models and typed Entity constants from the shared schema. The Windows package currently implements the 32 entity collectors listed in `../docs/collector-mappings.md`, each with only its documented fields. This is an in-progress implementation, not a claim of complete Windows support.

```csharp
using DeviceReadout;
using DeviceReadout.Windows;

using var access = WindowsDeviceAccess.Create();
var fast = access.WithPollInterval(TimeSpan.FromMilliseconds(250));
RamSnapshot ram = await fast.Get(Entities.Ram, cancellationToken);
await foreach (var value in fast.Watch(Entities.Ram, cancellationToken)) {
    Render(value);
}
```

Configuration copies share the owning execution context but preserve their own settings. Dispose the context after use. Reads, discovery, normalization and native subscription setup/release run on a dedicated background lane. A 128-item request queue and 2048-item input/output stream queues prevent unbounded accumulation; sensor watches also have a 64-item lifecycle queue. Overload fails explicitly. Polling does not overlap or deduplicate samples.

Collector adapters can supply state changes through `IDeviceCollector.ObserveChanges`. Native callbacks copy their payload and submit a deferred read; the SDK performs collection and normalization on the worker with the configured deadline. Cleanup for already-owned subscriptions has reserved admission even when the ordinary read queue is full. If a native call outlasts the caller's deadline, disposal remains queued until that lane can run it.

Stream cancellation, observer errors and iterator `DisposeAsync` finish without waiting for native subscription cleanup. DisposeAsync is not a native release-completion barrier. Late registration results retain cleanup ownership even if cancellation wins the await; late callbacks cannot schedule another read. Cleanup remains on the worker and may wait for a stuck native operation to return. See the [129-check state lifetime verification](../docs/verification/2026-11-17-dotnet-state-lifetime.md) for held-cleanup behavior, repeated registration races and actual Windows unregistration evidence.

`IDeviceCollector` extends `IDisposable` with default no-op cleanup. DeviceAccess owns its collector and disposes it once on the worker after tracked subscriptions stop, including for an unused context. Configuration views share this ownership; use a distinct collector instance for independent contexts.

UI state is supplied through `access.Observers.Target/Publish/Current/Remove`. Permission state is supplied through `Observers.Permission`; register an app-owned coordinator with `Observers.OnPermissionRequest`. The coordinator is responsible for dispatching platform UI work to the app's UI dispatcher. SDK reads never invoke permission UI. `Permissions.Request` awaits observed state without the read timeout.

Native and app-registered targets have separate identities even when kind and ID match. `EntityAddress.Observed` and `PermissionRequest.Observed` preserve that distinction; permission coordinators must include it when routing requests by address. App-owned inventory takes precedence in List, while earlier native handles remain usable. Explicit Current retains the selected handle's source. Target failures/removal stay scoped; family failures cover both sources. Target registration accepts an unbound kind, and SensorSource requires an app-registered sensor. See the [125-check target identity verification](../docs/verification/2026-11-17-dotnet-target-identity.md), including the added positional permission-record component and remaining scope.

Permission checks and pending requests inherit the entity-kind observation when a target has no explicit status. A target observation, including null, takes precedence. Updating a kind status does not complete a request whose target has its own override.

`access.Observers.Failure(entity, new DeviceReadoutException(...))` reports a target or whole-collection observer failure. Permission status and collection failure are separate inputs: an app-owned permission observer publishes both `PermissionStatus.Denied` and `ErrorCode.PermissionDenied` when revocation prevents collection. This requires no SDK UI lookup or prompt.

Each adapter can own a separate failure slot with `using var failure = access.Observers.FailureSource(entity)`. Call `failure.Publish(error)` to report a typed failure and `failure.Publish(null)` to clear only that slot. Disposing the handle releases its own failure permanently and is safe to repeat. Application policy takes priority; a provider's recovery or disposal cannot clear application policy, another provider or its replacement.

Failures invalidate observed values and end affected streams, including native polling/event streams. Pending observed first-state reads receive the typed error. Native Get/List/Current/Describe discard a result if a matching failure occurred during that call, even if already cleared. `Observers.Failure(entity, null)` clears the gate; recovery needs fresh state, and does not restart old streams or revive removed handles. Fresh state may be published while failed before clearing. Native subscription cleanup runs on the collection lane.

Application sensor sources attach through `Observers.SensorSource(sensor, subscribe, description)`, where `sensor` comes from `Observers.Target`. The returned disposable owns that registration and permanently retires its target when released. Duplicate sources for one target are rejected. `subscribe` runs on the collection worker and receives `SensorObserverSession<T>` with `SamplingRate`, `CancellationToken`, `Publish(T)` and `Fail(DeviceReadoutException)`. It returns native listener cleanup or null. Each get/watch has its own session; a session failure leaves siblings alive. Registration, discovery and metadata are passive. The entity determines metadata kind; normalization and collection timestamps remain worker-owned.

`Observers.SensorActivity(false)` suspends sensor sessions while retaining pending watches; `true` starts fresh sessions with their original settings. This works while the consumer is between reads. Inactive get retains its overall timeout, while the watch first-sample timer runs only for an active session. Event watches wait for real occurrences without an event deadline. State queries remain available. The SDK does not infer inactivity from desktop focus or query UI/lifecycle state.

See the [121-check sensor-source verification](../docs/verification/2026-11-17-dotnet-sensor-sources.md) for cancellation, source lifetime and remaining native/physical integration scope.

`SnapshotJson.Serialize(snapshot)` uses camelCase fields and decimal strings for 64-bit byte/counter values. It preserves platform thermal-state tags. Public snapshot deserialization is not provided.

Cancellation links dispatch downstream callbacks asynchronously. Native subscription cancellation has a separate scope from the SDK's stream-control callbacks, so a slow native callback cannot hold the caller's error notification, context disposal, read deadline or cancellation. Native cleanup stays on the collection worker and may remain pending until native work finishes. See the [ownership and cancellation checkpoint](../docs/verification/2026-11-17-dotnet-observer-cancellation.md), which records 115 passing checks and the remaining matrix.

Run `tools/test-dotnet.ps1` from PowerShell at the repository root. It prefers the project-local SDK when present, otherwise uses `dotnet` from PATH. The console verification executable exits nonzero on any failed assertion and includes real Windows API queries when running on Windows. The projects currently use only the .NET runtime and have no external NuGet dependencies.

Windows battery targets are discovered with `await access.Batteries.List(token)` and read/watched through the same typed API. They represent individual OS device-path/tag generations; a tag change requires re-discovery and never revives an old handle. Native tags can change without a physical replacement. Empty slots are omitted, and a failed inventory cannot erase already observed removals or silently turn inaccessible batteries into an empty list.

The first battery discovery registers native interface notifications before enumerating devices. The context retains removal history between reads and after watches close; same-path/same-tag reappearance gets a fresh handle. A read spanning observed removal is discarded, and active watches fail without waiting for their next poll. DeviceAccess closure unregisters on the worker. See [interface lifetime verification](../docs/verification/2026-11-11-windows-battery-hotplug.md) for native registration evidence, controlled removal tests and physical-device limitations.

Individual battery reads preserve signed power, native voltage, chemistry, capacities and available time/temperature fields. Current is derived from same-status power and voltage when both have usable physical units. Relative capacities supply a ratio only; they are not exposed as energy or power. Missing fields remain null, and native handles are disposed on completion/failure. Power and Battery watches combine native power-setting callbacks with serial polling. Captured power-state values are retained; aggregate capacity notifications trigger a selected-pack read without substituting their percentage. See [battery fields](../docs/verification/2026-11-11-windows-battery.md) and [power-event verification](../docs/verification/2026-11-11-windows-power-events.md).

`Batteries.Current()` selects the OS aggregate battery. `List()` includes that logical target alongside individual devices; compare handles directly (`battery == current`) to distinguish it, and do not add its capacities to the individual pack capacities. The aggregate remains readable with `Present=false` when no battery is present. It uses native WinRT reports for separate design/full/remaining energy, signed charge power and status, plus available system remaining-time seconds. ReportUpdated subscriptions and WinRT initialization/reference cleanup run on the worker. Entity handles compare and hash by target and owning context, including across configuration views. See [aggregate verification](../docs/verification/2026-11-11-windows-aggregate-battery.md) for mappings, native evidence and limitations.

Individual watches also own a cancellable, read-only overlapped driver status wait on a separate background lane. Captured status values survive later native changes, while polling covers fields outside the driver's change conditions. Unknown capacity disables capacity thresholds; unsupported waits retain polling. Cancellation drains native completion before freeing buffers and does not block the caller or shared collection worker. One watch's closure does not stop another. See [status and I/O verification](../docs/verification/2026-11-11-windows-battery-status.md) for controlled battery inputs, actual kernel transport checks and remaining physical-driver evidence.

`CpuCores.List()` exposes active logical processors with group-aware indices and physical core/package relationships. Get/watch validate each target against fresh topology; observed removal retires its handle permanently. Reads run on the collection worker and never change affinity or power settings. ProcessorInformation supplies current/maximum Hz where its native processor numbers can be mapped unambiguously. See [CPU verification](../docs/verification/2026-11-11-windows-cpu.md) for native and independent CIM evidence and WOW64/multi-group clock limitations.

`Cpu.AvailableLogicalProcessorCount` reads current process affinity, default CPU sets and reservation eligibility. It counts distinct logical processors in the process-default pool without converting CPU-time percentages into CPU counts or aggregating explicit per-thread overrides. Ambiguous multi-group/wide WOW64 mappings and observed configuration races return null for this field. Get/watch reflect native configuration changes without modifying them. See [live CPU availability verification](../docs/verification/2026-11-11-windows-cpu-availability.md) for native child tests, controlled reservation inputs and remaining limitations.

`NetworkInterfaces.List()` returns context-owned generation handles. A successful inventory or read that observes removal permanently retires the old handle and its active watches; reappearance creates a new target. IP interface/address/route notifications supplement polling and queue fresh reads on the worker. The context shares three native registrations and releases them on closure. Protocol-level deletion does not imply whole-adapter removal. See [network verification](../docs/verification/2026-11-11-windows-network.md) for actual native registration/cancellation, controlled transition evidence and remaining rapid-reuse/field gaps.

Network snapshots include selected-interface IPv4/IPv6 `Routes`, with destination prefixes and scoped gateways. On-link routes have a null gateway; a successful empty table is an empty list, while unavailable/malformed route data leaves only Routes null. MTU uses IPv6 properties when IPv4 is unavailable. All native queries and buffer cleanup stay on the worker. See [route and MTU verification](../docs/verification/2026-11-11-windows-network-fields.md) for controlled cases and an independent C comparison of actual Windows route counts/layout.

`Get(Entities.WindowsPublisherIdentity)` returns the native publisher-context ID as lowercase hexadecimal and its typed TPM/UEFI/registry source. Each field remains independently nullable; no replacement identifier is generated. Watch uses initial collection and serial polling, preserving equal values. WinRT activation, reads and cleanup stay on the worker. Unpackaged Win32 apps and packages without a publisher ID share the native system ID; it is not an app-installation ID or a universally permanent hardware serial. See [identity verification](../docs/verification/2026-11-11-windows-publisher-identity.md) for actual reads, restricted-process behavior and persistence/version limits.

`Get(Entities.NetworkPath)` reads the Windows preferred/default profile's connection state, OS internet classification and metering. Other path fields currently remain null; limited connectivity is not reported as a confirmed captive portal or constrained-data mode. Watch combines native NetworkStatusChanged notifications with polling. Callbacks enqueue fresh worker reads and do not query OS state or invoke UI. Registration denial is a typed error, while an unimplemented event source retains polling. See [network path verification](../docs/verification/2026-11-11-windows-connectivity.md) for actual native registration/removal, independent WinRT comparison and unverified custom-route/network-transition cases.

`Get(Entities.NetworkPerformance)` reads the preferred profile's DataPlanStatus inbound/outbound rates in bit/s. Absent rates remain null and zero is preserved; RTT, effective type and browser state remain null. Watch combines native status notifications with serial polling and retains equal values. Path and performance watches share a worker/runtime but keep their typed snapshots and subscription lifetimes separate. No active speed measurement is performed. See [performance verification](../docs/verification/2026-11-11-windows-network-performance.md) for rate mapping, partial errors, deadlines, actual null-rate evidence and remaining physical-provider cases.

`List(Entities.WifiConnection)` discovers active Wi-Fi connections; `Current` selects the preferred Windows profile only when it is Wi-Fi. Get/watch supply SSID, selected authentication and native signed RSSI. BSSID, frequency and current link speeds remain null pending their native adapters. No scan, location-sensitive BSSID query or implicit permission request is performed. Observed disconnection/network replacement retires old handles, including native WLAN not-found/disconnected results. Native status events supplement equal-value polling. App permission observations and blocking failures remain separate inputs. See [profile verification](../docs/verification/2026-11-11-windows-wifi.md) and [RSSI verification](../docs/verification/2026-11-11-windows-wifi-signal.md) for mappings, the 94-check suite, native client cleanup/deadlines and the current host's absence of a connected Wi-Fi profile.

`List(Entities.CellularSubscription)` discovers native mobile broadband accounts. `Current` selects an unambiguous account associated with the preferred active WWAN path. Get/watch provide account carrier, slot, GSM home MCC/MNC, current data technology and roaming; CountryCode remains null. Network status events supplement polling. Permissions remain app-observer inputs, and get/watch never request UI. See [cellular verification](../docs/verification/2026-11-11-windows-cellular.md) for the 101-check suite, six held-call deadline cases and the actual empty account inventory. The [account-watcher checkpoint](../docs/verification/2026-11-11-windows-cellular-watcher.md) extends this to 109 checks and one shared native source across contexts. Observed removals persist between reads, stale in-flight results are rejected and late old-source callbacks cannot affect a fresh source. Unsupported native events retain polling. Physical modem fields/events, slot notifications, unobserved reuse and suspend/resume integration remain pending.

`Sensors.List(Entities.Illuminance)` and `Sensors.List(Entities.Pressure)` discover Windows LightSensor and Barometer targets. Describe provides kind, available device name and minimum report interval. Get/watch return lux or pascals through native current readings and ReadingChanged events; equal readings are retained. Explicit frequency requests share the selected sensor's report interval, clamp to its native minimum and restore the previous interval after the final subscription ends. PlatformDefault keeps the existing native cadence when no numeric request is active. Discovery and capability deadlines cancel their owned native asynchronous enumeration. See the [136-check scalar sensor checkpoint](../docs/verification/2026-11-17-windows-scalar-sensors.md) for native versus controlled evidence and remaining physical/hotplug coverage.

`Sensors.List(Entities.Gyroscope)` and `Sensors.List(Entities.Magnetometer)` use the same discovery and lifecycle API. Get/watch provide one Vector3 per native reading, in rad/s and microteslas respectively. The native device axes are retained without screen-orientation compensation. An unreadable or nonfinite component makes the entire Value null; a subsequent complete sample recovers without restarting the watch. Native calls check cancellation between component reads. See the [140-check vector sensor checkpoint](../docs/verification/2026-11-17-windows-vector-sensors.md) for ABI measurement, held-read and actual inventory evidence.

`Sensors.List(Entities.Accelerometer)`, `Sensors.List(Entities.LinearAcceleration)` and `Sensors.List(Entities.Gravity)` request the Standard, Linear and Gravity native selectors respectively. They share the Accelerometer factory while retaining distinct typed targets and measurement sources. Native G-force components are multiplied by -9.80665 to match the common acceleration sign and m/s² units; Windows face-up -1 G becomes common +9.80665 on Z. Opening a target verifies its native ReadingType before measurement; a mismatched kind permanently retires that handle. No derived filtering substitutes another acceleration kind. Activity changes and explicit blocking permission failures release and reacquire native observations through the existing observer contract. See the [144-check acceleration checkpoint](../docs/verification/2026-11-17-windows-acceleration.md).

`Sensors.List(Entities.AbsoluteOrientation)` and `Sensors.List(Entities.RelativeOrientation)` select the corresponding native reference kinds. Get/watch return named unit quaternions in the device-to-reference direction; absolute reference is east/magnetic-north/up, while relative reference belongs to the native session. No SDK initial-pose rebasing or display compensation is applied. Reference-kind mismatch retires the handle, and an unreadable/invalid quaternion returns null without ending the stream. Native property references are released after cancellation, including delayed reads. See the [148-check orientation checkpoint](../docs/verification/2026-11-17-windows-orientation.md).

`Sensors.List(Entities.ProximityNear)` and `Sensors.List(Entities.ProximityDistance)` expose independent native Boolean and meter measurements. Distance descriptions also provide MaximumRange in meters when available. False, zero and null remain distinct. Windows proximity has no report-interval API, so sampling-rate settings preserve native cadence and all equal events. Get/watch never create a display controller. Synchronous native opening and nullable-field reads remain on the worker for get/describe; delayed calls do not hold caller deadlines or context disposal. See the [152-check proximity checkpoint](../docs/verification/2026-11-17-windows-proximity.md).

`Sensors.List(Entities.HingeAngle)` returns native hinge targets. Get/watch convert double degrees to radians, including zero and a full turn, and preserve native event cadence without modifying angle thresholds. Metadata exposes kind and available name; the angular threshold is not a sampling interval or resolution. A first native event can complete a request before GetCurrentReadingAsync finishes, canceling the unused initial operation. Late initial values do not follow newer events. See the [156-check hinge-angle checkpoint](../docs/verification/2026-11-17-windows-hinge.md).

`Sensors.List(Entities.HumanPresence)` selects native human-presence targets. Get/watch expose Presence as true/false/null, preserving duplicate events and distinguishing unknown from absence. Engagement and distance are not used to infer presence. Descriptions provide Kind and available Name only. App-owned capability declarations and permission/activity observation control access; the SDK does not request permission or change presence/display settings. Required runtime interfaces can be unavailable on older Windows installations. See the [161-check human-presence checkpoint](../docs/verification/2026-11-17-windows-human-presence.md), including caller-token cancellation, native cancellation propagation and synchronous initial-value ordering corrections. Actual native consent and physical measurements remain unverified.

`Sensors.List(Entities.RelativeAltitude)` exposes zero or one default Windows altimeter; `Current(Entities.RelativeAltitude)` resolves the same typed target. Each open validates the native device ID, so a changed default cannot substitute for an old target. Get/watch return signed native meters with the platform's relative baseline, nullable failures and duplicate events. Metadata exposes Kind and available MinimumInterval; sampling requests share and restore the native report interval. See the [165-check relative-altitude checkpoint](../docs/verification/2026-11-17-windows-relative-altitude.md). Physical baseline/default-device behavior remains unverified. Windows Pedometer totals remain unmapped to StepCountSinceBoot until their required boot-based meaning can be established.
